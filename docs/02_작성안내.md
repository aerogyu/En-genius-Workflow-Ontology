# 02. 작성 안내 — 메모장으로 분야 하나 쓰기

대상: 워크플로를 손으로 쓰는 엔지니어 (먼저 Leo). 필요한 것은 **메모장**과 **더블클릭** 뿐이다.
설계 배경은 `docs/01_설계.md`, 사내 설치는 `README_offline.md`.

DB 로 비유하면: YAML 파일 = 행 입력 양식, `check.bat` = 입력 검증, `build.bat` = ETL(적재 파일 TTL 만들기) + 보고서 + 그림,
계약(interface) = 표 정의(컬럼·형·단위), 레지스트리 = 일련번호 발급 대장.

## 0. 한눈에

1. 폴더 하나 = 워크플로 하나. 그 안에 `_plan.yaml` 1개 + 분야마다 `<분야>.yaml` 1개.
2. 폴더를 **`scripts\check.bat` 위에 끌어다 놓는다** → 오류가 0 이 될 때까지 고친다 (1초 남짓).
3. 폴더를 **`scripts\build.bat` 위에 끌어다 놓는다** → 흐름 그림(`workflow.html`)이 브라우저로 열린다.

(선택) 메모장 대신 VS Code 로 쓰면 칸 이름 자동완성·모양 오류 물결 밑줄(노란색 — check 에서는 오류)·칸 설명이 나온다 — 1-1장. 빌드 결과를 표로 묻는 것은 `query.bat` — 7장.

## 1. 준비

- **연습**: `workflows\examples\short` 폴더를 통째로 복사해 바탕화면 같은 곳에 두고 거기서 고친다.
  저장소의 예시 폴더를 직접 고치면 저장소 파일이 바뀐다 (`build.bat` 기본 폴더도 예시이니, 예시 자체는 고치지 않는다).
- **사내 실제 작성**: `data\real\workflows\` 폴더를 만들고 거기에 쓴다 (git 에 올라가지 않는 곳). 이 폴더가 있으면 `check.bat`·`build.bat` 을 그냥 더블클릭해도 이 폴더를 쓴다.
  예시 폴더를 복사해 시작할 때는 **`_registry`·`_released` 폴더는 빼고** 복사한다 — 예시의 일련번호 대장을 실데이터에 쓰면 G01 오류.
  거꾸로 **실데이터 폴더(대장 포함)는 `data\real\` 아래에서만 빌드된다** — 바탕화면 등 밖으로 복사해 실험하면 G01 오류.
  실험은 `data\real\` 아래 다른 이름의 폴더에 복사해서 하거나, `_registry` 를 빼고 복사한다 (그러면 일련번호가 새로 붙는다).
- 메모장 저장은 **인코딩 UTF-8** (Windows 11 메모장 기본값). 'ANSI' 로 저장하면 읽기는 하지만 Y01 경고가 난다.
- 들여쓰기는 **스페이스 2칸**. 탭 금지(Y02) — **들여쓰기뿐 아니라 값 사이·주석 앞·줄 끝에도**. 칸이나 주석을 맞추려고 Tab 키를 누르거나
  엑셀 표를 붙여 넣으면 생기는데 화면에서는 띄어쓰기처럼 보인다 — check 가 그 줄을 `label:<탭>탈설계점 해석` 처럼 탭 자리를 드러내 보여 준다.
  한글 입력 상태에서 누른 스페이스(전각 공백)도 금지(Y02) — 한/영 키를 영문으로.
- 확장자는 **`.yaml`** (`.yml` 은 읽지 않는다 — `.bat` 이 주의 줄로 알려 준다).
- 폴더 이름·파일 이름에는 한글을 써도 된다. 인명은 파일 이름에도 쓰지 않는다.

## 1-1. VS Code 로 쓰기 (선택 — 자동완성·물결 밑줄·설명)

메모장 대신 **VS Code + Red Hat YAML 확장**으로 쓰면 칸 이름 자동완성, 선택지 목록, 모양 오류 물결 밑줄, 칸 위에 마우스를 올리면 한국어 설명이 나온다.
DB 비유: 입력 양식(YAML)에 **입력 마스크**를 씌우는 것 — 칸 이름·형식·선택지는 쓰는 동안 잡고, 참조·흐름 같은 업무 규칙 검사는 여전히 `check.bat` 이 한다.
스키마 파일은 `schema\generated\wfo_authoring.schema.json` (빌드가 쓰는 정본 모양 검사와 별도 — 손으로 쓰는 짧은 표기를 그대로 받는 작성용).

**준비 (한 번)**

1. **확장 설치** — 사내 VS Code 1.90.2 에는 **Red Hat YAML 1.25.0** (`redhat.vscode-yaml-1.25.0.vsix`, 반입 — `README_offline.md` 1장). 2.0 이상은 VS Code 1.91 이상이 필요해 맞지 않는다.
   확장 탭(`Ctrl+Shift+X`) → 위쪽 `…` (Views and More Actions) → **Install from VSIX…** → vsix 파일을 고른다.
   (cmd 로는 `code --install-extension redhat.vscode-yaml-1.25.0.vsix`)
2. **폐쇄망 설정** — `Ctrl+Shift+P` → **Preferences: Open User Settings (JSON)** → 맨 바깥 `{ }` 안에 아래 두 줄을 넣는다.
   이미 다른 줄이 있으면 **그 마지막 줄 끝에 쉼표(`,`)** 를 찍고 그 아래에 넣는다 (JSON 은 줄 사이에 쉼표가 있어야 한다).

   ```jsonc
       "yaml.schemaStore.enable": false,
       "redhat.telemetry.enabled": false
   ```

   설정 화면(`Ctrl+,`)에서 하려면: 검색어 `yaml schema store` → 'Schema Store: Enable' 끄기, 검색어 `redhat telemetry` → 'Telemetry: Enabled' 끄기.
   왜: 확장이 인터넷의 스키마 목록(schemastore.org)을 받으려 하고 사용 통계를 보내려 한다 — 폐쇄망에서는 실패 알림만 뜨지만 꺼 둔다.
3. **스키마 잇기 — YAML 파일 맨 위에 한 줄** (권장):

   ```yaml
   # yaml-language-server: $schema=file:///C:/Engenius/engenius-workflow-ontology/schema/generated/wfo_authoring.schema.json
   ```

   - 경로는 사내 저장소 자리(`README_offline.md` 2장)를 `file:///` + 슬래시(`/`)로 적은 것. 다른 자리에 풀었으면 그 경로로 (Windows 라 대소문자는 상관없다).
   - 절대 경로라 **바탕화면 복사본에서도** 그대로 된다. `#` 주석 줄이라 build·check 에는 영향이 없다.
   - `_plan.yaml`·분야 파일 모두 **같은 한 줄** — 스키마는 하나다 (아래 '왜 하나인가').

   또는 settings.json 에 **매핑** — `data\real\workflows` 의 YAML 에 한 번에 (파일마다 줄을 붙이지 않아도 된다). 2번처럼 쉼표에 주의:

   ```jsonc
       "yaml.schemas": {
         "file:///C:/Engenius/engenius-workflow-ontology/schema/generated/wfo_authoring.schema.json": ["**/data/real/workflows*/*.yaml"]
       }
   ```

   (글롭을 읽는 방식이 확장 판에 따라 조금 다를 수 있다 — 안 붙으면 맨 위 한 줄 방식으로. 둘 다 있으면 보통 맨 위 한 줄이 먼저다.)
4. **확인** — YAML 을 열고 `label:` 같은 칸 이름 위에 마우스를 올린다 → 한국어 설명이 뜨면 연결된 것. 빈 줄에서 `Ctrl+Space` → 칸 이름 목록.
   오른쪽 아래 상태 표시줄이 `UTF-8`(저장 인코딩, 기본값)·`Spaces: 2`(Tab 키가 스페이스를 넣음)인지도 본다 — Y01·Y02 를 미리 막는다.
   저장하기 전에 **문제 패널(`Ctrl+Shift+M`)** 을 연다 — 밑줄이 그어진 자리가 ⚠ 항목으로 줄마다 모인다 (항목을 누르면 그 줄로 간다).

**밑줄 색 — 노란 물결도 고친다**
- **노란(주황) 물결 = 스키마(모양) 위반.** 확장 1.25.0 은 스키마 위반을 모두 '경고' 로 표시한다 (문제 패널의 ⚠ — 설정으로 바꿀 수 없다).
  그러나 check 에서는 **같은 것이 S01~S04 오류**다 (rc 1, 결과 파일 없음). '경고' 라고 넘기지 않는다.
- **빨간 물결 = YAML 문법 오류** (따옴표 짝·들여쓰기 등 — 문구는 영어, 한국어 안내는 check 의 Y 코드).
- 빌드 칸·담당자 칸에는 영어 `Matches a schema that is not allowed.` 와 한국어 설명(예: '빌드가 계산하는 칸 — 적지 않는다', 칸 이름에 취소선으로 보일 수 있다)이
  함께 뜬다 — 둘 다 '이 칸을 지운다' 는 뜻이다.

**되는 것**

| 무엇 | 예 |
|---|---|
| 칸 이름 자동완성 (`Ctrl+Space`) | 단계 안에서 `in` → inputs. 빈 파일에서는 '_plan.yaml 골격'·'분야 파일 골격', 목록 아래에서는 단계·계약·루프 골격 (Tab 으로 다음 칸) |
| 선택지 목록 | `phase:` · `status:` · 항목 `type:` · `transfer:` (정식 값 + 별칭 `수기`·`메일` …) · 긴 형식 `unit:` 후보 (단위 목록) |
| 노란 물결 = 모양 오류 (check 의 S 코드와 같은 것 — check 에서는 **오류**) | 모르는 칸·오타(S01) · 담당자류 칸(S01) · `{ }` 한 줄 안의 쉼표 목록·천 단위 쉼표 (`{…, formats: pdf, docx}` → 모르는 칸 'docx' — `[pdf, docx]` 로, `maximum: 1,000` → `1000`) · key 형식, 계약 판 세 자리, TOOL ID, 확장자, 선택지 밖, 참거짓·정수 칸(S02) · 필수 칸 빠짐(S03) · 빌드가 계산하는 칸(S04) · 항목 한 줄 `첫칸 \| 설명 \| 선택` 의 규칙(빈 첫칸 U01, `\|` 셋 이상·셋째 칸이 '선택' 아님·`file:` 뒤 확장자 S02) · 참조 칸에 key 형식이 아닌 것 (예 `tools: Gas Turb` — 어느 것도 가리킬 수 없다) |
| 마우스 설명 | 칸마다 뜻·짧은 표기·관련 check 코드. items 에서는 첫칸 표와 단위 목록 |

**안 되는 것 — 여전히 `check.bat`** (편집기는 파일 하나의 **모양**만 본다)
- 참조가 실제로 있는지(R01 — 예 `if-cycle-db` 오타), key 중복(R02, 다른 파일), plan 이 전체에서 한 번인지(R04)
- 단위(U01·U02 — 단위 목록은 자동완성 후보·설명으로만), 항목 규칙(C), 데이터 연결(D), 흐름·루프(F·L), 판(V), 레지스트리(G), 메모 속 인명(P01)
- YAML 문법(들여쓰기 탭·`%`·따옴표 — 확장 자체도 빨간 물결을 긋지만 문구는 영어. 한국어 안내는 check 의 Y 코드)
- **값 사이·주석 앞·줄 끝의 탭** — YAML 1.2 는 그 자리의 탭을 띄어쓰기로 받으므로 편집기는 조용할 수 있다 (확장 안에서는 확인 못 함). check 는 Y02 로 그 줄을 가리킨다
- → 밑줄이 없어도 **저장한 뒤 `check.bat`** 을 누른다. 밑줄과 check 결과가 다르면 아래 '알려진 차이' 를 본다 — check 만 잡는 것(위 목록)은 check 를 따르고,
  편집기만 긋는 것(빈 빌드 칸·필수 칸 `null` 등)은 고쳐 두면 된다 (잃는 값이 없다).

**YAML 1.2 와 '전부 글자'** — 확장은 YAML 1.2 로 읽어 `version: 0.1`·`1.10` 을 숫자로, `true` 를 참거짓으로 본다. 빌드는 모든 값을 글자로 읽는다 (2장 덧붙임).
스키마는 이 차이를 감안해 두었다 — `0.1`·`1.10`·`yes`·`예`·`o` 에 따옴표를 달 필요가 없고 밑줄도 없다 (마우스 설명에 숫자로 보여도 빌드는 글자 그대로 읽는다).

**알려진 차이** (드묾 — `tests/test_authoring.py` 가 고정한다)
- 편집기가 더 엄격 (check 는 통과 — 고쳐 두면 된다): 값이 빈 **빌드 칸**(`members:` — check 는 아는 칸의 빈칸을 '안 적은 것' 으로 넘긴다, 지운다) ·
  필수 칸에 글자로 쓴 `null`·`~` 는 빈칸으로 본다 (check 는 글자 'null' 로 받는다 — 그런 값은 쓰지 않는다) ·
  따옴표 안 앞뒤 공백 (`transfer: '수기 '` — check 는 공백을 떼고 읽는다, 공백을 지운다) ·
  사내 `data\real\config\rules.yaml` 에 더한 전달 방법 별칭·참거짓 낱말은 스키마에 없어 밑줄 (스키마는 저장소 `config\` 기준 — 그 줄은 check 결과를 따른다).
- 편집기가 더 너그러움 (check 를 따른다): YAML 1.2 가 숫자·참거짓으로 바꾼 값은 원래 글자를 모른다 — 예 `key: True` 는 밑줄이 없지만 check 는 S02 (key 는 소문자),
  `max_iterations: 10.0`·`0x0a` 처럼 YAML 1.2 가 정수로 읽는 꼴도 마찬가지 (check 는 S02 '정수') · 값 사이 탭(위).
- (차이 아님 — 2026-10-20 판부터) 값이 빈 **모르는 칸·담당자 칸**은 check 도 S01 이다. `{ }` 한 줄 안의 쉼표 목록(`formats: pdf, docx`)·천 단위 쉼표(`1,000`)가
  쉼표 뒤 조각을 '값 없는 칸' 으로 만들기 때문이다 — 예전 check 는 그 조각을 조용히 버려 값을 잃었다 (화면 안내: '{ } 안의 목록은 [a, b]').

**왜 스키마가 하나인가** — 빌드는 모든 YAML 파일을 같은 모양으로 읽는다 (절은 전부 선택, plan 이 전체에서 한 번인지는 파일을 합친 뒤 R04).
`_plan.yaml` 용과 분야 파일용으로 나누면, 분야 파일에 tools 를 둔 것처럼 빌드는 받는데 편집기만 밑줄을 긋는 경우가 생긴다.

**예시 파일에는 그 한 줄을 넣지 않았다** — ① 절대 경로는 설치 자리마다 다르고, 상대 경로(`../../../schema/…`)는 1장대로 바탕화면에 복사한 연습 폴더에서 깨진다
(확장이 스키마를 못 읽었다는 알림을 띄울 수 있다). ② 예시의 행 번호가 6장 실수 표·`tests/test_mistakes.py` 골든의 기준이라 한 줄을 더하면 행이 모두 밀린다.
→ 연습 복사본에는 위 한 줄을 각 파일 맨 위에 붙여 넣는다 (그러면 행 번호가 하나씩 밀린다 — 화면의 행 번호는 늘 그 파일 기준이라 문제없다). `data\real\workflows` 는 settings.json 매핑으로 한 번에.

**스키마 다시 만들기** — `schema\wfo.yaml`·`config\rules.yaml`·`config\units.yaml` 을 고쳤으면 `schema.bat` (작성용 스키마도 같이 만든다 — `schema.bat --check` 가 드리프트를 본다).
이 스키마는 개발 PC 에서 파이썬 검사기(jsonschema)와 YAML 1.2 흉내로만 시험했다 — 확장 안에서의 문구·자동완성 모양은 사내에서 처음 본다 (이상하면 증상만 값 없이 알려 준다).

## 2. 규칙 5줄

1. 파일 하나 = 분야 하나. 맨 위에 `discipline: cmp` 를 적고 그 아래에 `steps` / `interfaces` / `loops` 를 둔다. 공통 목록(plan, disciplines, tools, components)은 `_plan.yaml` 에 둔다.
2. 모든 것은 **key**(영문 소문자·숫자·하이픈, 예 `cmp-meanline`)로 부른다. key 는 전체 파일에서 하나뿐이어야 한다. 이름을 바꿀 때는 새 key 에 `renamed_from: 옛-key` 를 적는다 (일련번호 IRI 가 이어진다).
3. 단계에는 **inputs, outputs, tools** 만 적는다. 선후와 병렬은 빌드가 계산한다 ("B 의 입력 = A 의 출력" 이면 A→B). 데이터 없이 순서만 있는 선후는 `after` 에 적는다. 목록은 `a, b` 로 써도 된다
   — 단 **`{ … }` 한 줄 묶음 안에서 여럿이면 `[a, b]`** (`{key: cool, label: 냉각, related_parts: [COOL, SAS]}`). `{ }` 안에서는 쉼표가 칸을 나눠
   `related_parts: COOL, SAS` 의 `SAS` 가 칸 이름으로 읽힌다 (S01 '모르는 칸 SAS'). 같은 까닭으로 숫자에는 천 단위 쉼표를 쓰지 않는다 (`1000`).
4. 계약 항목은 **`이름: 단위 | 한국어 설명 [| 선택]`** 한 줄로 쓴다. 숫자 항목은 단위가 필수이고, 무차원은 `1`, 퍼센트는 `퍼센트` 로 쓴다. 선택지나 범위가 필요하면 `{type: enum, values: […]}` 같은 긴 형식을 쓴다.
5. 반복은 `loops` 에 **back_from(끝), back_to(처음), until(수렴 메모), initial(첫 바퀴 값)** 을 적는다. 루프는 back_from 단계가 있는 파일에 둔다.

덧붙임: 값은 전부 글자로 읽는다. 그래서 `version: 0.1`, `yes`, `no`, `1.10` 에 따옴표를 달 필요가 없다 (예전 YAML 처럼 숫자·참거짓으로 바뀌지 않는다).
참/거짓은 그 칸이 참/거짓 칸일 때만 바뀐다 (`external`·`deliverable`·`required`·`list` 칸에서 `true`·`yes`·`예`·`참`·`o` / `false`·`no`·`아니오`·`거짓`·`x`).
`#` 뒤는 주석이다 — 메모는 주석이나 `note:` 칸에.

## 3. 완결 예시 — 성능→압축기, 계약 2개, 루프 1개

`workflows\examples\short\` 의 파일 3개 그대로다. `check` 결과는 오류 0 · 경고 0 · 참고 3.

```yaml
# _plan.yaml — 워크플로 머리·분야·툴 목록 (전체에서 한 번)
plan: {key: concept-design, label: 개념설계 워크플로 (교과서 예시), phase: 개념설계, version: 0.1}

disciplines:
  - {key: perf, label: 성능}
  - {key: cmp,  label: 압축기}

tools:                                  # tool_id 는 사내에서 link-tools 후보를 보고 사람이 적는다
  - {key: gasturb, label: GasTurb}
  - {key: excel,   label: Excel}
```

```yaml
# perf.yaml
discipline: perf                        # 이 파일의 단계·계약은 성능 분야

steps:
  - key: perf-cycle
    label: 설계점 사이클 해석
    tools: gasturb
    inputs: if-cmp-map                  # 압축기 맵 — 루프로 되돌아오는 데이터 (아래 loops 는 cmp.yaml)
    outputs: if-cycle-dp

interfaces:
  - key: if-cycle-dp
    label: 설계점 사이클 결과
    version: 0.1.0
    items:                              # 한 줄 = 이름: 단위 | 한국어 설명 [| 선택]
      W2:   kg/s | 압축기 입구 유량
      PR_c: 1    | 압축기 압력비
      Tt4:  K    | 터빈 입구 전온도
      BPR:  1    | 바이패스비 | 선택
```

```yaml
# cmp.yaml
discipline: cmp

steps:
  - key: cmp-meanline
    label: 압축기 1D 평균반경 설계
    tools: excel
    inputs:
      - {interface: if-cycle-dp, transfer: 수기}   # 사이클 결과를 엑셀에 손으로 옮김 → Tool Agent 후보
    outputs: if-cmp-map

interfaces:
  - key: if-cmp-map
    label: 압축기 특성 맵
    version: 0.1.0
    items:
      map_file:     file:csv | 맵 파일 (속도선별 수정유량·압력비·효율)
      surge_margin: 퍼센트   | 설계점 서지 마진
      map_source:   {type: enum, values: [1D 상관식, 3D CFD, 시험], label: 맵 출처}

loops:                                  # 되돌아가는 간선 하나 = 루프 하나. 몸통은 빌드가 계산
  - key: loop-cmp-match
    label: 압축기–사이클 매칭
    back_from: cmp-meanline             # 여기서
    back_to: perf-cycle                 # 여기로 되돌아간다
    until: 맵을 반영한 사이클 재정합에서 추력 오차 1 % 이내 (예시 값, 판정은 엔지니어)
    initial: 첫 바퀴는 맵 없이 설계점 효율 가정값
    monitor: if-cmp-map.surge_margin
    max_iterations: 5
```

빌드가 계산하는 것 (적지 않는다):
- 선후 perf-cycle → cmp-meanline (if-cycle-dp 를 나름, ✋ 수기 구간).
- 루프 몸통 [perf-cycle, cmp-meanline], 나르는 계약 if-cmp-map. perf-cycle 의 if-cmp-map 입력은 '루프' 종류 (첫 바퀴에는 없다 → initial).
- `수기` → `메일·수기 전달`, `퍼센트` → `%` 로 읽는다 (참고 U03).

더 큰 예시(하위 단계·묶음 2단·외부·최종 계약·동결 1건·6분야 레인)는 `workflows\examples\textbook\`.

| `components:` | key\*, label\*, broader, note | 구성품 (선택). broader = 상위 구성품 key |
| `tools:` | key\*, label\*, tool_id, label_at_link, not_in_survey, note | label = 화면 이름(공개 상용명). tool_id = Tool 온톨로지 TOOL ID (`TOOL-000123` 꼴, **사람이** link-tools 후보를 보고). label_at_link = 그때의 Tool 온톨로지 이름. not_in_survey = 조사 대상이 아닌 이유 (적으면 X04·X05 안내를 끈다) |

**분야 파일 (`<분야>.yaml`)** — 맨 위 `discipline: <분야 key>` 한 줄.

| 절 | 칸 | 뜻 |
|---|---|---|
| `steps:` | key\*, label\*, tools, inputs, outputs, after, part_of, when, components, status, discipline, note, renamed_from | tools = 툴 key 목록. after = 순서만 있는 앞 단계 key. part_of = 상위 단계 key (하위 단계일 때). when = 조건 메모. status = 초안·검토중·확정. discipline 은 파일 머리와 다를 때만.<br>**하위 단계 묶음**: 상위 단계도 steps 에 한 항목으로 둔다 (없으면 part_of R01). 상위 단계에는 보통 key·label·note 만 — inputs/outputs 를 적으려면 하위 단계들의 경계(묶음 밖과 주고받는 것)와 똑같이 (다르면 F03 경고), tools 는 하위 단계에. 그림·루프 몸통·선후에는 상위 단계 하나로 나온다 (하위 단계는 그림 말풍선·'하위 단계' 표·질의 Q1/Q2 에서 보인다) |
| inputs 한 건 | interface\*, transfer, tool, format, note | 짧게 `inputs: if-a, if-b` 도 된다. transfer = 전달 방법 (5장). tool = 이 데이터를 받는 툴 key (그 단계 tools 중 하나). format = 파일 확장자 (예 csv) |
| outputs 한 건 | interface\*, tool, format, note | 짧게 `outputs: if-a` |
| `interfaces:` | key\*, label\*, version\*, items\*, records, status, external, deliverable, discipline, note, renamed_from | version = 세 자리 판 (0.1.0). status = 초안·검토중·확정·대체됨. external: true = 워크플로 밖에서 들어옴(만드는 단계 없음이 정상). deliverable: true = 최종 산출물(받는 단계 없음이 정상) |
| items 한 줄 | `이름: 첫칸 \| 설명 \| 선택` | 이름 = 영문으로 시작, 영문·숫자·`_` (W2, PR_c). 첫칸은 아래 표. 대소문자만 다른 이름(Pt·pt)은 C11 오류 |
| items 긴 형식 | `이름: {type, unit, label, description, required, list, min_items, minimum, maximum, values, formats, ref}` | type 기본 number, required 기본 필수. minimum·maximum 은 숫자(number·integer), values 는 enum, formats 는 file 항목에만 뜻이 있다 (다른 형에 적으면 C10 오류) |
| records 한 건 | name\*, label, items\* | 계약 안의 묶음 (표 모양 데이터, 예 맵 = 속도선 > 점). name 은 대문자로 시작 (MapPoint) |
| `loops:` | key\*, label\*, back_from\*, back_to\*, until\*, initial, monitor, max_iterations, include, note, renamed_from | back_from = 끝 단계(여기서), back_to = 처음 단계(여기로). until = 수렴 메모 (판정은 엔지니어). initial = 첫 바퀴 값 출처. monitor = `계약key.항목` (여럿이면 목록). include = 매 반복 같이 돌릴 곁가지 단계 |

**항목 한 줄의 첫칸**

| 첫칸 | 뜻 | 예 |
|---|---|---|
| 단위 기호 (5장 표) | 숫자 (number) | `Tt4: K \| 터빈 입구 전온도` |
| `1` / `퍼센트` | 무차원 / % | `PR_c: 1 \| 압력비` |
| `int` (또는 `정수`) | 정수 (단위 1) | `n_stages: int \| 단수` |
| `text` (또는 `문자`) | 글자 | `station: text \| 스테이션 번호` |
| `bool` (또는 `참거짓`) | 참/거짓 | `converged: bool \| 수렴 여부` |
| `file:csv,txt` (또는 `파일:`) | 파일 (허용 확장자, 소문자·점 없이) | `map_file: file:csv \| 맵 파일` |

## 5. 값 목록

**단위** (`config\units.yaml` — 목록에 없으면 U02 오류. 새 단위는 한 줄 더한다: 사내 `data\real\` 아래 폴더의 실작성이면 `data\real\config\units.yaml`,
바탕화면 같은 연습 폴더면 저장소 `config\units.yaml` — `data\real\config\` 덮어쓰기는 `data\real\` 아래 폴더를 빌드할 때만 쓰인다.
U02 의 '혹시 …' 는 표기만 다른 같은 단위일 때만 고른다 — 괄호 안 종류를 보고, 배율·종류가 다르면(`kg/h` ≠ `kg/s`) 새 단위로 더한다)

| 종류 | 적는 표기 |
|---|---|
| 무차원 | `1`, `%` (별칭 `퍼센트`·`pct`·`무차원`) |
| 온도 / 온도차 | `K`, `degC` (별칭 `°C`·`℃`) / `dK` (절대온도와 온도차는 다른 종류) |
| 압력 (절대압 기준 — 게이지압이면 설명에) | `Pa`, `kPa`, `MPa`, `bar` |
| 질량유량 | `kg/s` (별칭 `kg/sec`) |
| 길이·면적 | `m`, `mm` · `m2` (별칭 `m²`·`m^2`) |
| 속도·각도·회전속도 | `m/s` · `deg` · `rpm` (별칭 `r/min`) |
| 시간 | `s` |
| 동력·힘 | `kW`, `MW` · `N`, `kN` |
| 비에너지·비열 | `J/kg` · `J/(kg.K)` |

대소문자를 가린다 (`MPa` ≠ `mPa`) — 대소문자만 다르면 U02 가 맞는 표기를 알려 주지만 자동으로 고치지는 않는다.

**전달 방법** (`transfer` — Tool 온톨로지 '전달 방법' 선택지 + 미상)

| 정식 값 | 짧게 써도 되는 것 (`config\rules.yaml`) |
|---|---|
| 파일 저장 | 파일 |
| PDM 등록 | PDM |
| DB 기록 | DB |
| 메일·수기 전달 | 수기, 메일 ← **Tool Agent 후보** (그림의 굵은 주황 ✋, 질의 Q2) |
| 타 SW 직접 연동 | 직접, 연동 |
| 미상 | — |

앞 단계·루프에서 오는 입력에 transfer 를 안 적으면 참고 D07 로 건수를 알려 준다 (수기 구간을 찾으려면 적는다).

**그 밖의 선택지**: phase = 개념설계 · 기본설계 · 상세설계 / 단계 status = 초안 · 검토중 · 확정 / 계약 status = 초안 · 검토중 · 확정 · 대체됨 / 항목 type = number · integer · string · boolean · enum · file · struct.

S01(오류) '모르는 칸 docx' + '값이 빈 칸 — { } 한 줄 안에 쉼표로…' — `{ }` 안에 쉼표 목록(`formats: pdf, docx`)이나 천 단위 쉼표(`maximum: 1,000`)를 쓴 것: `[pdf, docx]`·`1000` 으로.
`enum:A, B, C` 는 선택지 셋이다 (`enum:A/B/C` 와 같다).
코드 전체 목록은 `docs/01_설계.md` 4장 표.

**루프가 여럿일 때**
- 같은 단계로 되돌아가는 루프 여럿(예: 압축기 맵·터빈 맵·이차유로 유량이 각각 사이클 해석으로)은 **분야마다 하나씩 그대로 적는다** — 빌드가 한 반복으로 묶어 계산한다 (경고 없음, L08 에 '같은 처음 … 와 한 반복').
- 안쪽 루프(예: 터빈 1D ↔ 냉각 유량)를 바깥 루프(사이클) 안에 두는 것도 그대로 적는다 — 안쪽 루프 단계는 바깥 루프 몸통에 들어간다.
- L04(경고) '엇갈려 겹친다' 는 **처음(back_to)이 다른** 두 루프가 일부 단계만 같을 때다. 화면에 겹치는 단계가 나온다.
  한 반복이 다른 반복을 통째로 품게 하려면 바깥 루프의 `include` 에 안쪽 몸통 단계를 더하거나(바깥 루프 처음의 하류일 때만 — 아니면 L09) back_to 를 고친다. 따로 도는 반복이면 그대로 둬도 된다 (경고만).

## 7. 빌드 결과 읽는 법

**화면 (= `report.txt`)** — 한 줄이 메시지 하나:

```text
[경고 X02] _plan.yaml 23행  툴 'gasturb' 의 TOOL-900005 는 TOOL-900001(GasTurb) 로 통합됨
        → tool_id 를 TOOL-900001 로 바꾸고 label_at_link 도 갱신
== 오류 0 · 경고 1 · 참고 5
== 코드별 건수 (값 없음 — 밖으로 가져갈 수 있는 줄): 경고 X02 1 · 참고 D07 1, L08 1, U03 1, X04 1, X05 1
TTL: 작성 427 + 파생 222 트리플 · 단계 7 · 계약 7 (JSON Schema 7) · 루프 1 → …\output\20261019T224700_textbook
Protégé 보기용: workflow_protege.ttl (트리플 1736 = 스키마 1064 + 작성 427 + 파생 217 + 머리 4 + 외부 어휘 선언 24) — 보기 전용, 고쳐도 YAML 로 돌아가지 않는다
```

- `[수준 코드] 파일 행  문구` 다음 줄 `→` 가 고치는 법 (있을 때). 행 번호는 메모장 '줄' 번호 (메모장 `Ctrl+G`).
- **오류** = 결과 파일을 만들지 않는다 (rc 1). **경고** = 만들지만 확인할 것. **참고** = 알림 (예: L08 루프 몸통 요약, U03 단위 별칭).
- 순서는 오류 → 경고 → 참고. 모양 오류(Y·S)가 있으면 그 뒤 검사는 하지 않는다 — 먼저 그것부터 고친다.
  `_plan.yaml` 이 없으면(R04) 분야·툴 참조 검사도 하지 않고 R04 하나만 보인다. 파일 맨 위 `discipline:` 오타는 그 줄에서 R01 한 번만 나온다.
- YAML 문법 오류(Y03)는 원인 줄을 가리킨다 — 콜론 뒤 공백 빠짐(`tools:cfx`)·전각 콜론(`label：`)은 그 줄과 고치는 법이 바로 나온다.
- 수준은 사내에서 `data\real\config\rules.yaml` 의 `levels` 로 코드별로 바꿀 수 있다 (예 `R05: 참고`).

**출력 폴더 `output\<시각>_<폴더 이름>\`**

| 파일 | 무엇 | 어떻게 보나 |
|---|---|---|
| `workflow.html` | 흐름 그림 (build.bat 이 연다) | 레인 = 분야, 왼→오른 = 순서. 실선 = 데이터로 이어진 선후(선에 마우스: 계약), 점선 = 순서만, **굵은 주황 ✋ = 수기 전달 (Tool Agent 후보)**, **보라 ↺ = 반복 루프** (마우스: 몸통·나르는 데이터·수렴 조건·첫 바퀴), '수렴 뒤' 배지 = 어느 루프 몸통에도 들지 않고 루프가 끝난 뒤 한 번 도는 단계. 같은 열에 선후 없이 놓인 단계는 병렬. 하위 단계는 상위 단계 상자 하나로 그린다 — 상자에 '▸ 하위 단계 n개', 마우스를 올리면 하위 단계 이름·툴·받는 데이터(✋ 수기 표시). 아래에 **하위 단계 표**·루프 표(수렴 뒤 단계는 그 루프 기준)·계약 표 |

**질의 표 (`query.bat`)** — 빌드 출력에 역량 질의 q01~q08(`queries\*.rq`)을 돌려 결과를 **표로** 보인다. 읽기만 한다 (파일을 만들지 않는다).
DB 비유: 적재한 표에 미리 써 둔 SELECT 8개를 돌리는 것.

- **더블클릭** → 가장 최근에 **오류 없이 끝난** build 출력 (`output\<시각>_<폴더>\` 중 `workflow.ttl` 이 있는 것).
- **끌어다 놓기** → 그 build 출력 폴더(또는 그 안의 `workflow.ttl`). Tool 온톨로지 `survey.ttl` 을 **같이** 놓으면 교차 질의 q07·q08 의 조사 쪽 열이 채워진다
  (없으면 그 열이 비고 맨 끝에 '참고' 한 줄).
- cmd 에서: `scripts\query.bat [output\<실행>] [survey.ttl …] [q02 q03 …]` — 질의 이름을 주면 그것만.
- 화면: `== q02 Q2 수기 전달 입력 = Tool Agent 후보 … — 2행` 아래에 머리 줄·구분 줄·행. 맨 끝 `[query] RESULT: OK  (rc=0)`.
  q04 는 단계 key `cmp-map` 이 질의에 박혀 있다 (예시 값 — 다른 단계를 보려면 `queries\q04_upstream.rq` 의 그 글자를 바꾼다).
- 표에는 YAML 의 key·툴 이름이 그대로 나온다 — 사내 내용이니 밖으로 가져가지 않는다 (이 장 끝 '밖으로 가져올 수 있는 것').

**Protégé 로 보기 (보기 전용)** — DB 비유로 Protégé 는 '스키마(ERD)와 행을 한 화면에서 보는 뷰어' 다. 고치는 곳은 늘 YAML 이다.

1. Protégé 를 열고 **File > Open** 으로 출력 폴더의 `workflow_protege.ttl` 하나를 연다.
   (`workflow.ttl` 만 열면 클래스 정의가 없고, 스키마 OWL 만 열면 개체가 없다 — 그래서 합본을 만든다.)
   인터넷이 필요 없다 (가져오기 `owl:imports` 없음). 온톨로지 이름(IRI)은 `<워크플로 IRI>/protege`, 판(versionInfo)은 `_plan.yaml` 의 `version` 이다.
2. **한국어 이름으로 보기** — **View > Render by label (rdfs:label)**. Protégé 판에 따라 메뉴 이름이 조금 다를 수 있다 — View 메뉴의 'Render by …' 항목 중 label 을 고른다.
   그래도 한국어가 안 나오면 **File > Preferences > Renderer** 에서 언어 목록에 `ko` 를 앞에 둔다 (이것도 판에 따라 자리·이름이 조금 다를 수 있다).
   단계·계약·루프 같은 개체는 YAML 의 `label`(한국어)로, 클래스는 스키마의 영어 이름(Step·Interface …)으로, wf: 속성은 YAML 칸 이름(tools·inputs·outputs·members …)으로,
   외부 어휘(p-plan 등)는 라벨이 없어 접두 이름(p-plan:isPrecededBy)으로 보인다. 아래 괄호의 wf: 이름은 IRI 이름이다 (label 로 보면 칸 이름).
3. **Entities** 탭 (안 보이면 Window > Tabs > Entities) 의 하위 탭:
   - **Classes** — wf:Step·wf:Interface·wf:Loop 등과 그 위의 표준 클래스(p-plan:Step·p-plan:Plan·prov:Entity·skos:Concept)
   - **Individuals** — 단계·계약·변수·바인딩·루프·분야·툴 (판에 따라 'Individuals by class' 탭이 따로 있다)
   - **Object properties** — 개체 사이 관계: p-plan:isPrecededBy(앞 단계) · wf:produces·wf:consumes(내놓는·받는 계약) · wf:usesTool(= tools, 쓰는 툴) · wf:hasInput·wf:hasOutput(= inputs·outputs, 바인딩) · wf:loopMember(= members, 루프 몸통) …
   - Data properties — 글자·숫자 값 (전달 방법 wf:transfer, 단위 wf:unitCode(= unit) …)
4. 개체(예: 단계) 하나를 누르면 오른쪽 **Property assertions** 에 관계가 보인다 — 어느 단계 뒤인지(isPrecededBy), 어떤 계약을 받고 내놓는지, 어느 툴을 쓰는지, 전달 방법이 무엇인지.
   key(`skos:notation`)·정의·설명은 관계가 아니라 **Annotations** 에 보인다 (정상).
5. **Protégé 에서 고친 것은 YAML 로 돌아가지 않는다 (보기 전용).** 저장해도 그 파일만 바뀌고, 다음 build 는 YAML 에서 새로 만든다 — 고칠 것은 YAML 에 적고 build 를 다시 한다.
6. 추론기(Reasoner 메뉴 — HermiT 등)는 돌려 봐도 되지만 **결과(추론된 관계·불일치 표시)를 판정으로 쓰지 않는다.** 판정은 build 검사와 엔지니어가 한다. 이상하게 보이면 build 화면의 검사 결과를 먼저 본다.
   추론기는 **합본에서** 돌린다. 합본의 동결 일자(wf:releasedAt)는 `2026-10-19T00:00:00` 처럼 시각이 붙어 보인다 — HermiT 는 OWL 2 데이터타입 목록 밖의 `xsd:date` 가 있으면
   시작하지 않아서 합본에서만 `xsd:dateTime`(그날 00:00:00)으로 바꿔 넣었다 (정본 `workflow_derived.ttl`·`wfo.owl.ttl` 은 날짜 그대로). 그래서 `wfo.owl.ttl` 만 따로 열어 HermiT 를 돌리면 멈춘다.
   HermiT 로 실제 돌려 본 것은 아직 없다 (개발 PC 에 없음) — 다른 이유로 멈추면 그 오류 문구의 종류만(값 없이) 알려 준다.

합본에는 외부 어휘(p-plan·prov·dcterms·qudt·skos)의 속성·클래스 **선언**이 들어 있다 — 선언이 없으면 Protégé 가 그 술어를 주석으로 읽어 단계 사이 관계가 '관계' 로 보이지 않는다.
이 선언은 합본에만 넣고 정본 OWL(`schema\generated\wfo.owl.ttl`)은 바꾸지 않는다 (남의 어휘에 쓰지 않는다). 빌드 시각 기록(BUILD)은 빼서 **같은 YAML 이면 같은 파일**이 나온다.
Protégé 로 실제 열어 보는 확인은 사내에서 한다 (개발 PC 에는 Protégé 가 없어 RDF 문법·선언 규칙만 테스트했다).

**YAML 폴더 안에 생기는 것** — `_registry\ids.csv`(key → 일련번호 IRI 대장, 빌드가 관리), `_registry\origin.txt`(example | real), `_released\<계약>\<판>.json`(동결본). 손으로 고치지 않는다.

**밖(개발 PC)으로 가져올 수 있는 것** — 화면·`report.txt` **맨 끝 한 줄** `== 코드별 건수 (값 없음 — 밖으로 가져갈 수 있는 줄): …` 뿐이다 (예 "오류 U02 3, F01 1 · 경고 R05 2").
그 위의 메시지 줄에는 사내 key·이름·값·경로가 들어 있으니 옮기지 않는다 (손으로 세지 말고 그 줄을 쓴다).

## 8. 다음 단계 (필요할 때)

- **판 동결 (`release.bat`)** — 계약이 확정되면 YAML 폴더를 끌어다 놓고 계약 key·사유를 입력한다 (일자는 자동).
  사유에는 **무엇을 확인했는지만** 적는다 — 이름·직급('○○○ 책임 확인')이 보이면 다시 묻고, 끝내 그러면 V06 으로 거절한다.
  그 뒤 그 계약을 고치면서 판을 안 올리면 V02 오류가 '필요: MAJOR/MINOR/PATCH' 와 **올릴 판**(`→ version: 1.0.0 로 올린다`)을 알려 준다.
  MAJOR = 첫 자리 +1 (0.1.0 → 1.0.0, 0.x 에서도), MINOR = 둘째 자리 +1 (0.1.0 → 0.2.0), PATCH = 셋째 자리 +1 (0.1.0 → 0.1.1). 올림 규칙은 `docs/01_설계.md` 4장.
  - 다른 계약을 struct 로 품은 계약을 동결하면 품은 계약의 그때 정의도 같이 동결된다 — 품은 계약을 고치면 품는 계약도 판을 올리라고 한다.
  - 동결된 계약도 `renamed_from` 으로 개명할 수 있다 — 동결 이력이 이어지고 build 가 동결본을 새 key 폴더로 옮긴다 (데이터 봉투의 `contract` 는 새 key).
  - 동결본(`_released\…\<판>.json`)이 비었거나 깨지면 V08 오류가 그 파일을 가리킨다 — 지우고 release 로 다시 동결한다. `0.1.0 - 복사본.json` 같은 파일은 읽지 않는다 (V09 경고).
- **데이터 검사 (`validate.bat`)** — 실제 데이터 JSON 파일을 끌어다 놓는다. 가장 최근 build 출력의 계약으로 검사한다 (봉투: `{"contract": …, "version": …, "data": {…}}`).
- **툴 연결 (`link_tools.bat`)** — YAML 폴더와 Tool 온톨로지 survey.ttl 을 함께 끌어다 놓으면 TOOL ID 후보 CSV 가 나온다. 맞는 것을 `_plan.yaml` tools 의 `tool_id`·`label_at_link` 에 사람이 적는다.
- **개명** — key 를 바꾸면 옛 key 는 폐기(G02 경고)되고 새 일련번호가 붙는다. 같은 것이면 새 key 아래에 `renamed_from: 옛-key` 를 적는다 (G03 참고, IRI 유지).
  - **renamed_from 은 key 를 바꾼 뒤 첫 build 전에** 적는다 (check 를 먼저 누르면 G02 가 미리 알려 준다). build 로 새 key 가 이미 새 일련번호를 받은 뒤에 적으면 잇지 못한다 — G06 경고.
  - 옛 key 를 남겨 둔 채 복사본에 renamed_from 을 적거나, 같은 옛 key 를 둘이 적으면 G04 오류 (두 단계가 한 IRI 를 받게 되므로). 복사해 새로 만든 것이면 renamed_from 을 지운다.
  - 폐기된 key 를 다시 쓰면 예전 일련번호가 되살아난다 (G05 참고) — 다른 것이면 key 를 바꾼다.
- **질의** — `query.bat` (7장 '질의 표'). cmd 로 직접 치려면 **저장소 폴더에서 먼저 `call scripts\env.bat`** (코드를 설치하지 않으므로
  `PYTHONPATH=src` 와 UTF-8 모드 `PYTHONUTF8=1` 을 잡는다 — 또는 `README_offline.md` 9장처럼 `set PYTHONPATH=src` · `set PYTHONUTF8=1`.
  빼먹으면 `No module named engenius_wf`, UTF-8 모드가 꺼지면 한국어 파일을 cp949 로 읽는다) 그 뒤
  `.venv\Scripts\python -m engenius_wf query output\<실행> [q02 q03 …] [--table]` (질의 이름은 `--table` 앞에)
  (q01~q06; q07·q08 은 `--catalog <survey.ttl>` 과 함께. `--table` 없이는 탭으로 나눈 줄 — 엑셀에 붙여 넣기 쉽다). 질의 파일은 `queries\`.
