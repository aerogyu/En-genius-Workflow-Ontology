# 01. 개념설계 워크플로 온톨로지 — 설계 (v0.1)

2026-10-19 설계 제안서(승인)를 저장소 문서로 옮긴 것이다. **결정 Q1~Q4 는 Leo 가 전부 권장안으로 정했다 (2026-10-19, 7장).**
제안서의 시안(한 파일 `wf_build.py`·`wf_schema.py`)은 W0 에서 `src/engenius_wf/` 모듈로 이식했다 — 같은 입력에서 시안과 출력이 같다 (맨 끝 '검증 기록').

설계는 세 안(standards·authoring·contract)을 비교해 골랐다. 뼈대는 standards 안이다 (판정 2명 모두 승자로 골랐다).
여기에 authoring 안의 작성 층과 contract 안의 계약 관리를 붙였고, 판정자들이 지적한 공통 결함을 고쳤다.

---

## 1. 한 문단 요약

Leo 는 분야별 YAML 파일을 손으로 쓴다. YAML 은 **행 데이터 입력 양식**에 해당한다. 단계마다 적는 것은 받는 데이터(inputs), 내놓는 데이터(outputs), 툴 세 가지이고, 계약 항목은 `이름: 단위 | 설명` 한 줄로 적는다. 반복은 `loops` 에 '어디서 어디로 되돌아가는지' 한 줄로 적는다.
명령 하나(`scripts\build.bat`)가 **검사와 변환**을 함께 한다. 선후, 병렬, 루프 몸통, 루프가 끝난 뒤에 도는 단계는 빌드가 데이터에서 계산한다. 결과물은 다섯 가지다.
- TTL: DB 적재 파일. 작성분과 계산분을 그래프 2개로 나눈다.
- 계약별 JSON Schema: 데이터 계약 검사기.
- 흐름 그림 HTML
- 한국어 오류 보고서
- Protégé 용 OWL (`schema/generated/wfo.owl.ttl`)

스키마는 LinkML 파일 하나(`schema/wfo.yaml`)다. 이 파일이 **ERD** 역할을 하며, YAML 모양 검사, RDF 술어, SHACL 을 모두 여기서 만든다. 표준은 W3C 계열 어휘 몇 개(P-Plan, SKOS, PROV, QUDT 단위 IRI)에 한 방향으로만 맞춘다. 그래서 다른 시스템도 표준 어휘로 이 결과를 읽을 수 있다. Graph Studio PoC 와의 호환은 아직 확인하지 못했다(위험 1).
툴은 Tool 온톨로지의 TOOL ID 로 잇는다. ID 는 한 곳에만 사람이 적는다(HITL). 이렇게 하면 '수기 전달 구간 = Tool Agent 후보'를 워크플로 쪽에서 바로 뽑을 수 있다. 새로 반입할 패키지는 없다(LinkML, rdflib, pyyaml, jsonschema 는 Tool 온톨로지 반입 목록에 이미 있다 — `requirements.lock` 이 같다).

## 2. 개념 모델

ERD 로 보면 클래스가 표, 참조가 FK 다. 괄호 안은 RDF IRI 의 ID 접두이고, 레지스트리가 의미 없는 일련번호로 준다 (결정 Q1).

| 클래스 (표) | 뜻 | Leo 가 적는 칸 | 빌드가 채우는 칸 | 표준 정렬 |
|---|---|---|---|---|
| Workflow (PLAN) | 워크플로 머리 (개념설계) | key, label, phase, version | — | ⊑ p-plan:Plan |
| Discipline (DSC) | 분야 = 그림의 레인 (성능, 압축기, 연소기, 터빈, 냉각, 이차유로) | key, label, related_parts(사내, 선택) | — | ⊑ skos:Concept |
| Component (CPN) | 구성품 (선택) | key, label, broader | — | ⊑ skos:Concept |
| ToolRef (TRF) | 툴 이름표. **TOOL ID 는 여기 한 곳에만** | key, label, tool_id, label_at_link, not_in_survey | ontoTool → egid:TOOL-… | — |
| Step (STEP) | 단계 | key, label, tools, inputs, outputs, after(순서만), part_of(하위 단계), when(조건 메모) | isPrecededBy(데이터에서 도출, 늘 DAG), isStepOfPlan, MultiStep, hasInputVar, loopInputVar | ⊑ p-plan:Step |
| InputBinding / OutputBinding (INB/OUB) | 단계가 받거나 내놓는 데이터 1건 (연결표 행) | interface, transfer(전달 방법), tool, format | kind(앞 단계, 루프, 외부), variable | — |
| Interface (IFC) | **데이터 계약** = JSON 형식 1종 | key, label, version(0.1.0), status, external, deliverable, items, records | jsonSchema 파일 | — |
| InterfaceItem / Record (IFI/REC) | JSON 키 1개 / 계약 안의 묶음 (맵 = 속도선 > 점) | name, type(기본 number), unit, required(기본 필수), list, min/max, values, formats, ref | qudt:hasUnit, order | — |
| Loop (LOOP) | 반복 루프 = **되돌아가는 간선 1개를 객체로 둔 것** | back_from, back_to, until(수렴 메모), initial(첫 바퀴 값 출처), max_iterations, monitor, include | members(몸통), carries(나르는 계약), afterConvergence(수렴 뒤 단계) | (BPMN 루프 개념만 주석) |
| DataVariable (VAR) | (빌드) 워크플로 안의 데이터 1건 | — | conformsTo 계약, isOutputVarOf(실제로 만든 단계 1개 — SHACL maxCount 1) | ⊑ p-plan:Variable |
| InterfaceRelease (REL) | (빌드) 계약 동결 기록 = HITL 승인 기록 (인명 없음) | release 명령의 사유 | 일자, 사유, 옛 판 스키마 | ⊑ prov:Entity |
| SubPlan (SPLAN) | (빌드) 하위 단계 묶음의 하위 계획 | — | isSubPlanOfPlan(상위 단계가 속한 계획 — 워크플로 또는 위 하위 계획) | ⊑ p-plan:Plan |

레지스트리가 일련번호를 주는 것은 PLAN·DSC·CPN·TRF·STEP·IFC·LOOP 7종이다 (`src/engenius_wf/model.py` KINDS). 바인딩(INB/OUB)·항목(IFI)·묶음(REC)·변수(VAR)·동결 기록(REL)·하위 계획(SPLAN) IRI 는 레지스트리 ID 에서 해시로 만든다 — 재빌드해도 같다 (`src/engenius_wf/rdf.py`). 빌드 기록은 BUILD-<시각>·SRC-<해시>.

```
 Workflow ◄─isStepOfPlan─ Step ─usesTool─► ToolRef ─ontoTool··► egid:TOOL-000002 (Tool 온톨로지, 읽기만)
                          │ ▲
                 hasInput │ │ isPrecededBy  (빌드: "B 의 입력 = A 의 출력" 이면 A→B. 되돌림 간선은 넣지 않음 → 늘 DAG)
                          ▼ │
       InputBinding {transfer: 메일·수기 전달, tool: excel, format: csv} ─interface─► Interface ─hasItem─► InterfaceItem ─qudt:hasUnit··► unit:K
                          │                                                       ▲   └─hasRecord─► Record ─hasItem─► …
                          └─variable─► DataVariable ─────────── conformsTo ────────┘
                                         ▲ isOutputVarOf (만든 단계 1개)
                                         └ hasInputVar (받는 단계) / loopInputVar (루프로 되돌아온 입력 = 이전 반복 값)

 병렬 = 적지 않는다. 서로 경로가 없는 단계끼리가 병렬이다 (예: cmp-map ∥ cmp-cfd-check).

 반복 루프 (교과서 예시 workflows/examples/textbook)
   perf-cycle-dp ─if-cycle-dp─► cmp-meanline ─if-cmp-1d─► cmp-map ─if-cmp-map─► perf-offdesign
                                  ▲   │                                              │
                                  │   └─if-cmp-1d─► cmp-cfd-check  ◄ 수렴 뒤 단계     │
                                  └──────── Loop: back_from = perf-offdesign ────────┘
                                            back_to   = cmp-meanline
                                            until·initial = 메모 (판정은 엔지니어)
   빌드 계산:  members = [cmp-meanline, cmp-map, perf-offdesign]   (back_to 에서 back_from 으로 가는 길 위의 단계, + include — 안쪽 루프의 되돌림 간선도 길)
              carries = [if-perf-od]                              (되돌아가는 간선이 나르는 계약)
              afterConvergence = [cmp-cfd-check]                  (몸통 밖이지만 루프 안에서 바뀌는 데이터를 받음 → 수렴 뒤 1회.
                                                                   같은 back_to 루프가 여럿이면 그 몸통 합집합 밖)
```

**결정 근거 (짧게)**
- 루프를 '되돌아가는 간선 객체'로 둔다. 그래서 선후(isPrecededBy)는 늘 DAG 로 남는다. 표시 없는 순환은 오타로 보고 오류(F01)를 낸다. 이때 "loops 에 back_from: X, back_to: Y (추정)"을 안내한다.
- 루프로 되돌아오는 입력에는 `p-plan:hasInputVar` 를 달지 않고 `wf:loopInputVar` 로 따로 둔다. standards·authoring 시안에서는 P-Plan 변수 그래프가 순환이 되는 것을 실측했고, 이것이 그 결함의 수리다.
- 하위 단계가 있는 상위 단계(MultiStep)는 입출력을 경계 표시로만 쓴다. 'isOutputVarOf' 는 실제로 만드는 가장 깊은 단계 하나에만 단다.
- 첫 바퀴 문제는 Loop.initial(메모)로 다룬다. 빠뜨리면 경고(L07)한다. 데이터 봉투에는 `iteration: 0` 을 두어 첫 바퀴 가정값을 표시한다.
- 루프 하류(afterConvergence)는 '반복마다 결과가 낡는 단계'다. 판정자 2명이 함께 지적한 결함이라 빌드가 계산해 그림과 질의에 보인다. 매 반복 같이 돌려야 하는 곁가지는 `include` 로 몸통에 넣는다.
- **루프 여럿** (W1 검토 수리): ① 같은 back_to 로 되돌아가는 루프 여럿(압축기·터빈·이차유로 결과가 각각 사이클 해석으로 — 6분야의 기본 꼴)은 **한 반복**으로 본다.
  수렴 뒤 단계 = back_to 의 하류 중 같은 back_to 루프 몸통의 합집합 밖이고, 이 루프끼리는 L04 를 내지 않는다.
  ② 몸통의 '길'에는 **안쪽 루프**(back_to 가 다르고 두 끝이 모두 바깥 루프 back_to 의 하류)의 되돌림 간선도 든다 — 냉각↔터빈 안쪽 루프의 냉각 유량 단계는 바깥(사이클) 반복마다 다시 돈다.
  선후(isPrecededBy)·F01 은 지금처럼 되돌림 간선을 전부 뺀 그래프로 계산한다 (늘 DAG).
  ③ L04(엇갈림)는 back_to 가 다른 두 루프의 몸통이 일부만 겹칠 때만. 그림의 '수렴 뒤' 배지는 어느 루프 몸통에도 들지 않는 단계에만 단다 (루프 표·RDF 의 afterConvergence 는 루프별).
- **계약 하나 = 만드는 단계 하나** (결정 Q2). 이 규칙이 있어야 선후를 데이터에서 계산할 수 있다. 둘 이상이면 D01 오류.

## 3. YAML 작성 형식

작성자용 안내(메모장으로 분야 하나 쓰기, 칸 목록, 단위·전달 방법 선택지, 실수 표)는 **`docs/02_작성안내.md`** 가 정본이다. 여기에는 설계 요지만 둔다.

**규칙 5줄**
1. 파일 하나 = 분야 하나. 맨 위에 `discipline: cmp` 를 적고 그 아래에 `steps` / `interfaces` / `loops` 를 둔다. 공통 목록(plan, disciplines, tools)은 `_plan.yaml` 에 둔다.
2. 모든 것은 key(영문 소문자·숫자·하이픈)로 부른다. key 는 전체 파일에서 하나뿐이어야 한다. 이름을 바꿀 때는 `renamed_from` 을 적는다.
3. 단계에는 inputs, outputs, tools 만 적는다. 선후와 병렬은 빌드가 계산한다. 데이터 없이 순서만 있는 선후는 `after` 에 적는다. 목록은 `a, b` 로 써도 된다.
4. 계약 항목은 `이름: 단위 | 한국어 설명 [| 선택]` 한 줄로 쓴다. 숫자 항목은 단위가 필수이고, 무차원은 `1`, 퍼센트는 `퍼센트` 로 쓴다. 선택지나 범위가 필요하면 `{type: enum, values: […]}` 같은 긴 형식을 쓴다.
5. 반복은 `loops` 에 back_from(끝), back_to(처음), until(수렴 메모), initial(첫 바퀴 값)을 적는다. 루프는 back_from 단계가 있는 파일에 둔다.

값은 전부 글자로 읽는다 (`yaml.BaseLoader`). 그래서 `version: 0.1` 이나 `yes/no` 에 따옴표를 달 필요가 없다. 참/거짓은 스키마상 boolean 인 칸에서만 바뀐다.

**완결된 예시 — 성능→압축기, 계약 2개, 루프 1개.** `workflows/examples/short/` 의 파일 3개다. 빌드 결과는 오류 0, 경고 0 이다.

```yaml
# _plan.yaml — 워크플로 머리·분야·툴 목록 (전체에서 한 번)
plan: {key: concept-design, label: 개념설계 워크플로 (교과서 예시), phase: 개념설계, version: 0.1}
disciplines:
  - {key: perf, label: 성능}
  - {key: cmp,  label: 압축기}
tools:                                  # tool_id 는 사내에서 link-tools 후보를 보고 사람이 적는다
  - {key: gasturb, label: GasTurb}
  - {key: excel,   label: Excel}
```
```yaml
# perf.yaml
discipline: perf
steps:
  - key: perf-cycle
    label: 설계점 사이클 해석
    tools: gasturb
    inputs: if-cmp-map                  # 압축기 맵 — 루프로 되돌아오는 데이터
    outputs: if-cycle-dp
interfaces:
  - key: if-cycle-dp
    label: 설계점 사이클 결과
    version: 0.1.0
    items:                              # 이름: 단위 | 한국어 설명 [| 선택]
      W2:   kg/s | 압축기 입구 유량
      PR_c: 1    | 압축기 압력비
      Tt4:  K    | 터빈 입구 전온도
      BPR:  1    | 바이패스비 | 선택
```
```yaml
# cmp.yaml
discipline: cmp
steps:
  - key: cmp-meanline
    label: 압축기 1D 평균반경 설계
    tools: excel
    inputs:
      - {interface: if-cycle-dp, transfer: 수기}   # 사이클 결과를 엑셀에 손으로 옮김 → Tool Agent 후보
    outputs: if-cmp-map
interfaces:
  - key: if-cmp-map
    label: 압축기 특성 맵
    version: 0.1.0
    items:
      map_file:     file:csv | 맵 파일 (속도선별 수정유량·압력비·효율)
      surge_margin: 퍼센트   | 설계점 서지 마진
      map_source:   {type: enum, values: [1D 상관식, 3D CFD, 시험], label: 맵 출처}
loops:
  - key: loop-cmp-match
    label: 압축기–사이클 매칭
    back_from: cmp-meanline             # 여기서
    back_to: perf-cycle                 # 여기로 되돌아간다
    until: 맵을 반영한 사이클 재정합에서 추력 오차 1 % 이내 (예시 값, 판정은 엔지니어)
    initial: 첫 바퀴는 맵 없이 설계점 효율 가정값
    monitor: if-cmp-map.surge_margin
    max_iterations: 5
```
빌드가 계산한 결과는 다음과 같다.
- 흐름: perf-cycle → cmp-meanline. if-cycle-dp 를 나르고, ✋ 수기 구간이다.
- 루프 몸통: [perf-cycle, cmp-meanline]. 나르는 계약은 if-cmp-map 이다.
- perf-cycle 의 if-cmp-map 입력은 '루프' 종류다. 그래서 RDF 에서는 loopInputVar 로 들어가고, P-Plan 변수 그래프는 DAG 로 남는다.
- 생성물: 계약 JSON Schema 2개, 골격 예시 JSON 2개, TTL 168 트리플 (작성 104 + 파생 64).
- 짧은 표기 `수기` 는 `메일·수기 전달` 로, `퍼센트` 는 `%` 로 읽는다 (`config/rules.yaml` transfer_aliases, `config/units.yaml` aliases).
- Q2 질의(`queries/q02_manual_handoff.rq`) 결과 1행: 'GasTurb(perf-cycle) → Excel(cmp-meanline), if-cycle-dp, 수기'.

## 4. 빌드 명령이 만드는 것과 검사 규칙

**명령** (사내에서는 `scripts\*.bat` 더블클릭·끌어다 놓기로 쓴다. 모든 .bat 이 `scripts\env.bat` 을 거치고, env.bat 이 `PYTHONUTF8=1`·`PYTHONPATH=src` 를 설정한다.
.bat 의 인자 고르기·기본 폴더는 `scripts/bat_helper.py` 가 정한다 — `README_offline.md` 4장)

| 명령 (`python -m engenius_wf …`) | .bat | 하는 일 |
|---|---|---|
| `build <폴더> [--out 폴더] [--catalog survey.ttl …]` | build.bat | 검사 + 생성 전부. 오류가 있으면 결과 파일을 만들지 않는다 (rc 1). 기본 출력 `output/<시각>_<폴더 이름>/` |
| `check <폴더> [--catalog …]` | check.bat | 검사만 한다. 1초 남짓이라 작성 중에 자주 누른다 |
| `release <폴더> <계약> --reason "사유"` | release.bat | 확정 판을 동결한다 (HITL 기록은 일자와 사유만) |
| `validate <출력> <데이터.json…>` | validate.bat (끌어다 놓기) | 실제 데이터가 계약을 지키는지 검사한다 |

설정 파일 오류는 traceback 대신 `[NG] 설정 오류: …` 한 줄과 rc 2 로 끝난다.

**만드는 것** (`output/<실행>/`)
- `workflow.ttl`: 작성분. YAML 에 적힌 것을 그대로 옮긴다.
- `workflow_derived.ttl`: 계산분. 선후, 변수, 루프 몸통, P-Plan 이중 타입, PROV 빌드 기록이 들어간다.
- `workflow.trig`: 위 두 파일을 named graph 2개(`http://en-genius.local/graph/workflow`·`…/workflow-derived`)로 묶은 것. Fuseki 에 한 번에 올리는 용도다.
- `contracts/<계약>/<판>.schema.json` + `.example.json`
  - JSON Schema 2020-12 이고, 봉투 구조는 contract·version·produced_by·case·iteration·data 다.
  - data 는 닫힌 객체다. 항목마다 `x-unit`·`x-qudt-unit` 이 붙는다.
  - 파일 확장자 검사는 대소문자를 가리지 않는다.
  - 동결된 옛 판의 스키마도 계속 만든다. 동결된 판(현재 판 포함)의 스키마는 YAML 이 아니라 동결본의 정의로 만든다.
  - 다른 계약을 struct 로 품으면 그 계약은 `$defs/<계약 key>`(+ `x-interface` 판), 그 계약의 묶음은 `$defs/<계약 key>.<묶음>` — 두 계약의 같은 이름 묶음이 섞이지 않는다.
- `workflow.html`: 외부 JS 0, 다크 모드 지원.
  - 레인은 분야, 열은 위상 층이다.
  - 데이터 선후는 실선, 순서만 있는 선후는 점선이다.
  - 수기 전달은 굵은 주황 ✋, 루프는 보라 ↺ 로 그린다. 루프 툴팁에는 몸통, 나르는 계약, 수렴 메모, 첫 바퀴가 나온다.
  - 수렴 뒤 단계에는 배지를 단다. 아래에는 루프 표와 계약 표가 붙는다.
- `report.txt`: 오류·경고·참고를 코드와 함께 남긴다. 사내에서 밖으로 가져올 수 있는 것은 코드별 건수뿐이다. Tool 온톨로지의 diag 방식과 같다.
- `canonical.json`: 펼친 정본. LinkML 검증과 디버깅에 쓴다.
- 상태 파일은 **YAML 폴더 안에** 둔다: `_registry/ids.csv`(key → IRI), `_registry/origin.txt`(example | real), `_released/<계약>/<판>.json`.
  - 이렇게 하면 예시용 상태와 사내 `data/real/workflows/` 상태가 구조적으로 섞이지 않는다.
  - `origin.txt` 가 다르면 G01 오류를 낸다 (예시 대장 → 실데이터 폴더, 실데이터 대장 → data/real 밖 폴더 모두).
  - 레지스트리는 산출이 모두 끝난 뒤에 쓴다 — 중간에 실패하면 대장은 그대로다. check·release·link-tools 는 쓰지 않는다.

**검사 4층**: ① 읽기 → ② 모양 → ③ 의미 → ④ 산출. 모양 검사가 틀리면 그 자리에서 멈춘다. 연쇄 헛 오류를 막기 위해서다. 메시지마다 '파일 행 + 혹시 … + 고치는 법'이 붙는다.

판 올림 규칙은 다음과 같다 (`src/engenius_wf/versioning.py`).
- MAJOR: 항목 삭제, 필수 추가, 형·단위·목록·ref(품는 묶음·계약) 변경, 선택→필수, 범위 좁힘, 선택지 삭제, 묶음 삭제
- MINOR: 선택 항목 추가, 범위 넓힘, 선택지 추가, 묶음 추가
- PATCH: 계약·항목·묶음 이름(label)·설명만 변경
- 변화 아님: 항목·선택지 순서, 기본값과 같은 명시(`list: false`·`required: true`), 계약 key 개명(renamed_from — IRI 가 정체), 판 번호
- 품은 계약: 동결본은 struct 로 품은 다른 계약의 정의를 통째로 품는다(스냅샷). 품은 계약의 변화는 같은 규칙으로 품는 쪽의 올림 요구에 더해진다 (V02·V03).
- 개명: 동결된 계약을 renamed_from 으로 개명하면 옛 key 폴더의 동결본을 이어 읽고, build 가 새 key 폴더로 옮긴다 (봉투의 contract 값은 새 key).
- 동결본 쓰기는 임시 파일에 쓴 뒤 바꿔 끼운다 (중간 실패로 빈 동결본이 남지 않게). 동결 사유에 인명 유사 표기가 있으면 V06 으로 거절한다.

## 5. Tool 온톨로지 연결

- **단계는 툴 key 로만 부른다** (`tools: excel`). TOOL ID 는 `_plan.yaml` 의 tools 표 한 곳에만 둔다(`tool_id` + `label_at_link` 스냅샷).
  - 사내에서는 `link-tools` 가 사내 survey.ttl 로 후보 CSV 를 낸다. 근거는 '이름 일치', '비슷한 이름', '조사 누락 후보' 셋 중 하나다. 엔지니어가 보고 적는다. 빌드는 자동으로 채우지 않는다(HITL).
  - 저장소의 공개 예시는 합성 카탈로그 ID 만 쓴다 (`workflows/examples/catalog/tools_synthetic.ttl` 의 TOOL-9000xx, 형제 저장소 합성 survey.ttl 의 TOOL-000002). 합성 ID 는 실데이터에 재사용하지 않는다(G01).
- **코드가 아니라 RDF 로 잇는다.** survey.ttl(또는 Fuseki)을 읽기만 하고, 쓰는 술어는 4개다: `eg:Tool`, `skos:prefLabel/altLabel`, `eg:status`, `eg:merged_into` (`src/engenius_wf/tools.py` LINK_PREDICATES).
  - 이 4개를 두 저장소 사이의 '연결 계약'으로 문서화한다.
  - Tool 온톨로지 쪽에 '유지 테스트' 1건을 추가하는 일은 그 저장소를 바꾸는 것이라 Leo 결정이 필요하다(W5).
  - wf 쪽은 egid:TOOL-… 노드에 타입이나 라벨을 쓰지 않는다.
  - Q8(`queries/q08_tool_usage_cross.rq`)은 4술어 밖의 Tool 온톨로지 술어(툴사용·자동화 IF·입출력·방향·확장자·전달 방법)도 읽는다 — W5 유지 테스트 범위에 넣는다.
- **IRI 공간은 같은 egid:(`http://en-genius.local/id/`)를 쓰고, 유형 접두는 겹치지 않는다.**
  - Tool 온톨로지 지금 쓰는 접두: TOOL·USE·IO·CAT·FLD·LOAD (M4 에서 FEED·HANDOFF 예정)
  - 워크플로: PLAN·DSC·CPN·TRF·STEP·IFC·LOOP (일련번호) · INB·OUB·IFI·REC·VAR·REL·SPLAN (해시) · BUILD·SRC (빌드 기록)
  - Fuseki 한 데이터셋에 그래프만 나란히 올리면 매핑 없이 조인된다.
- **교차 질의가 이 연결의 핵심 가치다.**
  - Q2: 워크플로에서 '메일·수기 전달' 입력을 찾는다(Tool Agent 후보). Tool 온톨로지 M4 를 기다리지 않아도 된다.
  - Q8: 그 입력을 받는 툴의 조사 툴사용을 본다(자동화 IF, 입력 확장자, 전달 방법). 시안에서 Excel 14행이 나왔다. 그 가운데 USE-000002 는 csv 를 '메일·수기 전달'로 받는다고 신고돼 있어 워크플로와 조사가 일치했다 (합성 데이터).
  - M4 뒤 Q9: 워크플로상 이어지는데 Feed 가 없거나 Handoff(수기)인 툴 쌍.
- `transfer` 값은 Tool 온톨로지의 '전달 방법' 선택지 5개와 같게 하고 '미상'을 더한다. 짧은 별칭(수기, 메일, 파일, PDM, DB, 직접, 연동)은 `config/rules.yaml` 에 둔다. 그래서 Handoff 조인에 값 변환이 필요 없다.
- binding 의 `tool`·`format` 은 '단계×툴×계약×파일 형식'을 나타낸다. 한 단계에 툴이 여럿일 때 툴 쌍이 모든 조합으로 부풀어 Tool Agent 후보를 과대 산출하는 문제를 막고, Tool Agent 의 어댑터 대상(어느 툴의 어느 IO 가 이 계약을 실현하나)을 직접 적는다.
- 분야(6)와 파트(21)는 1:1 이 아니다. 기본 연결은 Tool 수준이다. 툴사용(파트×툴)으로 좁히고 싶으면 Discipline.related_parts(사내 파트 약칭)를 쓴다 (결정 Q3).

## 8. 위험

1. **P-Plan 은 W3C 표준이 아니다.** P-Plan 은 PROV 를 확장한 연구 어휘이고 유지 활동이 적다.
   - 정렬은 `schema/alignment.ttl` 한 파일이라 빼거나 바꾸기 쉽다.
   - Graph Studio PoC 가 P-Plan·PROV 를 아는지는 모른다. PoC 산출물 OWL 을 받아 대조해야 한다.
2. **루프 모델의 한계**
   - 같은 단계로 되돌아가는 루프 여럿(사이클↔압축기·터빈·이차유로)은 한 반복으로, 안쪽 루프(냉각↔터빈)는 바깥 몸통에 넣어 계산한다 (W1 검토 수리, 2장).
     back_to 가 다른 두 루프가 일부만 겹치면(엇갈림) L04 경고 — 몸통·수렴 뒤는 루프마다 따로 계산해 내보내지만 그 뜻(같이 도는지 따로 도는지)은 엔지니어가 판단한다.
   - 조건 분기는 메모(`when`)뿐이다.
   - '수렴 뒤 단계'는 루프 하류 중 그 반복 밖 전부라 큰 워크플로에서는 넓게 나온다 (그림 배지는 어느 루프 몸통에도 들지 않는 단계만).
   - 실제 6분야를 써 본 뒤(W4) 몸통 직접 지정 확장이 필요한지 다시 본다.
3. **'계약당 생산 단계 하나'(Q2)는 반복 갱신 실무와 부딪칠 수 있다.**
4. **손 작성 규모**
   - 6분야 × 20~40단계, 계약 100개 이상이면 한 사람이 쓰고 검토하기 무겁다.
   - 한 줄 문법, 기본값(type number, 필수), 골격 JSON 으로 줄이지만 실제 속도는 모른다.
   - 대안: 계약 항목만 엑셀로 쓰고 가져오는 보조 경로(W6).
5. **표준 IRI 이름은 기억에 기반한다.** QUDT 단위 꼬리(KiloGM-PER-SEC, REV-PER-MIN, J-PER-KiloGM-K 등)와 P-Plan 속성 이름은 원본과 대조하지 못했다. 틀리면 다른 시스템과 단위 맞추기가 조용히 실패한다(W1 대조).
6. **단위 의미가 얕다.** 절대온도와 온도차는 나눴다(K / dK). 게이지압과 절대압, 수정 유량·상대 회전수의 기준 조건은 설명 메모에만 의존한다.
7. **LinkML 생성기 함정은 정리 단계에 의존한다.** 정리 대상은 남의 어휘 덮어쓰기, 라벨 xsd:string, 같은 IRI 속성 경고, 열린 루트다 (`src/engenius_wf/schema_gen.py`). LinkML 판을 올릴 때마다 `schema --check` 와 SHACL 테스트로 다시 확인한다(1.11.1 고정).
8. **실데이터 경계**
   - 사내 실 워크플로, 계약 사양, 사내 툴명은 `data/real/workflows/` 에만 둔다. 이 PC 에는 교과서 예시와 공개 상용명만 둔다.
   - 인명은 담당자 칸을 스키마에서 거부한다(S01). 자유 텍스트는 패턴 경고(P01)뿐이라 HITL 검토가 남는다.
9. **두 저장소의 진화.** Tool 온톨로지 v0.4 에서 eg:status·merged_into 표현이 바뀌면 X 검사가 깨진다. 4술어 연결 계약과 테스트로 감시한다.
10. **확인하지 못한 것**
    - HermiT 일관성 검사 (owlready2 없음)
    - Protégé 로 열기. W1 에서 생성 OWL 의 OWL 2 DL 결함 셋은 고쳤다 — 값이 IRI 인 속성(wf:ontoTool·wf:structRef)은 객체 속성·xsd:anyURI 제약 제거,
      owl:versionInfo 클래스 제약 제거(판 필수·형식은 SHACL), 온톨로지 머리 하나(alignment.ttl 머리는 떼고 합침). OWL API 프로파일 검사에서 남는 것
      (외부 어휘·주석 속성 미선언 등 — 검토 때 스크래치에서 실측)은 따로 다룬다 (`docs/03` 4장).
    - Graph Studio 반입
    - 그림의 상호작용. 그림은 Edge headless 정적 캡처로만 봤다.
    - 6분야 규모의 그림 배치(간선 교차)
    - 사내 PC 에서의 실행 (개발 PC 에서 사내 흉내 — UTF-8 모드 꺼짐·Java 없음 — 로만 돌렸다)
